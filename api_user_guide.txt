AUTHENTICATION AND ERROR FORMAT
===============================

Protected endpoints require:
  Authorization: Bearer <token>

Tokens are returned by:
  POST /api/auth/login

Default token expiry:
  1 hour, unless AUTH_TOKEN_EXPIRES_IN_SECONDS is changed.

Normal API error shape:
  {
    "message": "Readable error message.",
    "code": "MACHINE_READABLE_CODE"
  }

Validation and authorization errors may include code. Unexpected server errors
return Status 500 with:
  {
    "message": "Internal server error."
  }


CURRENT DATABASE MODEL FOR AN EMPLOYEE
=======================================

The current PostgreSQL database was checked on 2026-08-19. The employee API is
backed by these relationships:

  users.id
    -> employees.user_id
    -> user_signatures.user_id

  overtime_plans.plan_id
    -> overtime_plan_items.plan_id
    -> overtime_plan_logs.plan_id
    -> overtime_plan_signature_records.plan_id
    -> notifications.plan_id

  approved Department OT Plan
    -> overtime_actual_periods.source_department_plan_id
    -> overtime_actual_entries.actual_period_id
    -> overtime_actual_comments.actual_entry_id

Important database constraints:
  users.role:
    admin, user, hr, supervisor, japanese_management

  users.status:
    active, pending, inactive

  employees.shift:
    day, night

  employees.status:
    active, inactive

  overtime_plans.period_type:
    weekly, monthly

  overtime_plans.plan_scope:
    employee, department

  overtime_plans.status:
    draft
    submitted
    submitted_to_supervisor
    supervisor_returned
    supervisor_accepted
    pending_approval
    returned_for_revision
    approved
    rejected
    closed

  overtime_plan_items.planned_hours:
    must be greater than 0

  overtime_plan_signature_records.status:
    active, superseded

  notifications:
    one notification per recipient and plan log

The employee-level account role is "user". A user can log in only when the user
account is active and it is linked to an employee profile. The authentication
middleware checks this relationship again on protected requests.

Employee names and email come from users. The employees table stores work-profile
data and links to users through user_id. Supervisor assignment uses
employees.supervisor_user_id. The legacy manager_id column may still exist in an
upgraded database, but it is not used by the current employee API response.

ACCOUNT SETUP PREREQUISITES
===========================

The account must be prepared before employee testing. Account creation and
signature upload are Admin-only; employee profile creation is available to Admin
or HR.

1. Create an active user with role "user".

   POST /api/admin/users
   or the compatibility route:
   POST /api/auth/register

2. Create or link the employee profile.

   POST /api/overtime/employees

   Example Admin/HR body:
   {
     "userId": "user-...",
     "departmentId": "DEP-RTD",
     "position": "Operator",
     "shift": "day",
     "employmentType": "regular",
     "supervisorUserId": "supervisor-user-..."
   }

3. Assign the employee signature as an Admin.

   POST /api/users/signature

   Body type:
     multipart/form-data

   Fields:
     userId     Text    users.id, not employees.employee_id
     signature  File    PNG or JPEG, maximum 2 MB

The signature is required by the preferred submit-and-sign endpoint. The image
is stored privately; the database stores its file path and MIME type.

5. LIST MY OVERTIME PLANS
=========================

Endpoint:
  GET /api/overtime/plans

Auth:
  Required user token

Supported query parameters:
  status
    One status, repeated status parameters, or comma-separated statuses.

  periodType
    weekly or monthly

  planScope
    employee or department

  dateFrom
    YYYY-MM-DD; includes plans whose period overlaps this date or later

  dateTo
    YYYY-MM-DD; includes plans whose period overlaps this date or earlier

  year
    1900 through 3000

  month
    1 through 12

  limit
    positive integer, maximum 100

  offset
    zero or a positive integer

Example:
  GET /api/overtime/plans?periodType=weekly&dateFrom=2026-08-01&dateTo=2026-08-31&status=draft,submitted_to_supervisor

Success:
  Status 200
  {
    "overtimePlans": [
      {
        "planId": "PLAN-...",
        "departmentId": "DEP-RTD",
        "departmentName": "RTD",
        "periodType": "weekly",
        "periodStartDate": "2026-08-17",
        "periodEndDate": "2026-08-23",
        "status": "draft",
        "planScope": "employee",
        "itemCount": 5,
        "plannedHours": 10,
        "createdBy": "user-...",
        "remarks": "Weekly planned overtime",
        "createdAt": "2026-08-18T01:00:00.000Z",

8. CREATE AN EMPLOYEE DRAFT WITH ITEMS (PREFERRED)
==================================================

Endpoint:
  POST /api/overtime/plans/draft

Auth:
  Required user token

Purpose:
  Atomically create the employee plan and all selected overtime entries. If any
  item is invalid, no partial plan or entries are committed.

Request body:
  {
    "periodType": "weekly",
    "periodStartDate": "2026-08-17",
    "periodEndDate": "2026-08-23",
    "remarks": "Weekly planned overtime",
    "items": [
      {
        "plannedDate": "2026-08-17",
        "plannedHours": 2,
        "reason": "Production support"
      },
      {
        "plannedDate": "2026-08-19",
        "plannedHours": 1.5,
        "reason": "Month-end preparation"
      }
    ]
  }

Rules:
  periodType, periodStartDate, periodEndDate, and a non-empty items array are required.
  Maximum 100 items.
  Each item requires plannedDate, plannedHours greater than 0, and reason.
  Each plannedDate must be within the plan period.
  The same date cannot appear twice in one employee draft.
  The backend assigns departmentId, planScope=employee, and employeeId.

Weekly period rule:
  Start on Monday, end on Sunday, exactly 7 calendar days.

Monthly period rule:
  Start on the first day and end on the last day of the same month.

Duplicate period rule:
  Multiple drafts for the same employee and exact period are allowed.
  A new draft is blocked if another plan for that user and exact period is already
  submitted or in workflow, including returned workflow states, approved, or closed.

Success:
  Status 201
  {
    "overtimePlan": {
      "planId": "PLAN-...",
      "periodType": "weekly",
      "periodStartDate": "2026-08-17",
      "periodEndDate": "2026-08-23",
      "status": "draft",
      "planScope": "employee",
      "itemCount": 2,
      "plannedHours": 3.5,
      "items": [],
      "logs": []
    }
  }

Important errors:
  400 PLAN_ITEMS_REQUIRED
  400 PLAN_ITEMS_LIMIT_EXCEEDED
  400 INVALID_WEEKLY_PLAN_PERIOD
  400 INVALID_WEEKLY_PLAN_START
  400 INVALID_MONTHLY_PLAN_PERIOD
  400 INVALID_MONTHLY_PLAN_RANGE
  400 PLAN_ITEM_DATE_OUT_OF_RANGE
  409 DUPLICATE_PLAN_ITEM_IN_REQUEST
  409 DUPLICATE_ACTIVE_EMPLOYEE_PLAN


9. REPLACE AN EMPLOYEE DRAFT (PREFERRED)
========================================

Endpoint:
  PUT /api/overtime/plans/:planId/draft

Auth:
  Required user token

Purpose:
  Atomically replace the editable plan fields and the complete item list.

Editable statuses:
  draft
  supervisor_returned
  returned_for_revision

Request body:
  {
    "periodType": "weekly",
    "periodStartDate": "2026-08-17",
    "periodEndDate": "2026-08-23",
    "remarks": "Revised weekly plan",
    "expectedUpdatedAt": "2026-08-18T01:00:00.000Z",
    "items": [
      {
        "plannedDate": "2026-08-18",
        "plannedHours": 2.5,
        "reason": "Revised support schedule"
      }
    ]
  }

Concurrency rule:
  expectedUpdatedAt is required and must equal the plan updatedAt value last read
  by the client. This prevents one browser session from silently overwriting a
  newer plan version.

Success:
  Status 200
  {
    "message": "Employee overtime draft saved successfully.",
    "overtimePlan": {
      "planId": "PLAN-...",
      "status": "draft",
      "updatedAt": "2026-08-18T02:00:00.000Z",
      "items": [],
      "logs": []
    }
  }

Important errors:
  400 PLAN_VERSION_REQUIRED
  400 PLAN_NOT_EDITABLE
  403 PLAN_DRAFT_ACCESS_DENIED
  409 PLAN_VERSION_CONFLICT
  409 DUPLICATE_ACTIVE_EMPLOYEE_PLAN

11. SUBMIT AND SIGN ATOMICALLY (PREFERRED)
==========================================

Endpoint:
  PATCH /api/overtime/plans/:planId/submit-and-sign

Auth:
  Required user token

Purpose:
  Submit the employee plan to the supervisor and create the employee signature
  audit record in one database transaction.

Request body:
  {
    "submissionRemarks": "Submitted for supervisor review.",
    "signatureRemarks": "I confirm these planned overtime entries."
  }

Compatibility body:
  {
    "remarks": "Submitted and confirmed."
  }

The single remarks value is used for both actions when separate values are not sent.

Prerequisites:
  The plan belongs to the authenticated user.
  The plan scope is employee.
  Status is draft, supervisor_returned, or returned_for_revision.
  The plan contains at least one item.
  The user and employee records are active.
  An Admin has assigned an active saved signature to the user.
  No other active employee plan exists for the same employee and exact period.
  No approved/closed Department OT Plan already finalizes that exact period.

Success:
  Status 200
  {
    "message": "Employee overtime plan submitted and signed successfully.",
    "plan": {
      "planId": "PLAN-...",
      "status": "submitted_to_supervisor",
      "submittedBy": "user-...",
      "submittedAt": "2026-08-18T03:00:00.000Z"
    },
    "signatureRecord": {
      "signatureRecordId": "PLANSIGNATURE-...",
      "planId": "PLAN-...",
      "employeeId": "EMP-...",
      "signatureOwnerUserId": "user-...",
      "actedByUserId": "user-...",
      "signerRole": "employee",
      "confirmationMethod": "self",
      "signatureFilePath": "users/user-.../signature.png",
      "signatureMimeType": "image/png",
      "signedAt": "2026-08-18T03:00:00.000Z",
      "remarks": "I confirm these planned overtime entries.",
      "status": "active"
    }
  }

Atomic behavior:
  If submission validation or signature creation fails, the full transaction is
  rolled back. The plan is not left half-submitted without its signature record.

Important errors:
  400 PLAN_HAS_NO_ITEMS
  400 PLAN_SUBMIT_NOT_ALLOWED
  400 SIGNATURE_REQUIRED
  400 EMPLOYEE_NOT_ACTIVE
  403 PLAN_SUBMIT_AND_SIGN_FORBIDDEN
  409 DUPLICATE_ACTIVE_EMPLOYEE_PLAN
  409 PLAN_PERIOD_ALREADY_FINALIZED


12. WITHDRAW A SUBMISSION
=========================

Endpoint:
  PATCH /api/overtime/plans/:planId/withdraw

Auth:
  Required user token

Purpose:
  Withdraw the employee plan before the supervisor has reviewed it and return it
  to draft for editing or deletion.

Request body:
  {
    "remarks": "I need to revise the planned dates."
  }

Alternative field:
  reason may be used instead of remarks.

Rules:
  A reason is required.
  The plan must belong to the authenticated user.
  The plan scope must be employee.
  Status must be exactly submitted_to_supervisor.

Success:
  Status 200
  {
    "message": "Employee overtime plan withdrawn successfully.",
    "plan": {
      "planId": "PLAN-...",
      "status": "draft",
      "submittedBy": "",
      "submittedAt": null
    }
  }

Database effects are atomic:
  Status returns to draft.
  submitted_by and submitted_at are cleared.
  rejection_reason is cleared.
  Active plan signature records become superseded.
  A submission_withdrawn activity log is created.
  Eligible recipients receive a notification from that plan log.

Important errors:
  400 PLAN_WITHDRAW_REMARKS_REQUIRED
  400 PLAN_WITHDRAW_NOT_ALLOWED
  403 PLAN_WITHDRAW_FORBIDDEN
  404 PLAN_NOT_FOUND

Once the supervisor accepts or returns the plan, withdrawal is no longer allowed.


13. DELETE MY PLAN
==================

Endpoint:
  DELETE /api/overtime/plans/:planId

Auth:
  Required user token

The plan must belong to the authenticated user.

Deletable statuses:
  draft
  supervisor_returned
  returned_for_revision
  rejected

Not deletable directly:
  submitted_to_supervisor
  supervisor_accepted
  pending_approval
  approved
  closed

To delete a plan still waiting for supervisor review:
  1. PATCH /api/overtime/plans/:planId/withdraw
  2. DELETE /api/overtime/plans/:planId

Success:
  Status 200
  {
    "message": "Overtime plan deleted successfully.",
    "overtimePlan": {
      "planId": "PLAN-..."
    }
  }

Deleting the plan cascades its plan items, logs, notifications, and plan signature
records according to the current database foreign keys.

Important error:
  400 PLAN_DELETE_NOT_ALLOWED


14. GRANULAR PLAN AND ITEM ENDPOINTS
====================================

These endpoints remain supported. For the current employee frontend, prefer the
atomic draft endpoints because they avoid partial saves.

14.1 Create an empty plan
-------------------------

  POST /api/overtime/plans

  Body:
  {
    "periodType": "weekly",
    "periodStartDate": "2026-08-17",
    "periodEndDate": "2026-08-23",
    "remarks": "Weekly planned overtime"
  }

  The backend assigns the employee department and planScope=employee.

14.2 Update plan fields
-----------------------

  PATCH /api/overtime/plans/:planId

  Editable statuses:
    draft, supervisor_returned, returned_for_revision

  Allowed employee fields:
    periodType, periodStartDate, periodEndDate, remarks

  departmentId changes are ignored for role user.

14.3 Add one item
-----------------

  POST /api/overtime/plans/:planId/items

  Body:
  {
    "plannedDate": "2026-08-17",
    "plannedHours": 2,
    "reason": "Production support"
  }

  Aliases:
    date instead of plannedDate
    totalHours instead of plannedHours

  The employeeId is assigned from the authenticated employee profile.

14.4 Add items in bulk
----------------------

  POST /api/overtime/plans/:planId/items/bulk

  Body:
  {
    "items": [
      {
        "plannedDate": "2026-08-17",
        "plannedHours": 2,
        "reason": "Production support"
      }
    ]
  }

  Maximum 100 items per request.

14.5 Update one item
--------------------

  PATCH /api/overtime/plans/:planId/items/:itemId

  Allowed fields:
    plannedDate or date
    plannedHours or totalHours
    reason

  A user cannot move an item to another employee.

14.6 Delete one item
--------------------

  DELETE /api/overtime/plans/:planId/items/:itemId

  The plan must belong to the user and be editable.

Common granular endpoint errors:
  400 PLAN_NOT_EDITABLE
  400 PLAN_ITEM_DATE_OUT_OF_RANGE
  400 INVALID_PLANNED_HOURS
  403 employee ownership error
  404 plan or item not found
  409 DUPLICATE_PLAN_ITEM
  409 DUPLICATE_PLAN_ITEM_IN_REQUEST


15. LEGACY SEPARATE SUBMIT AND SIGN ENDPOINTS
=============================================

These routes remain supported for compatibility. New employee clients should use
PATCH /api/overtime/plans/:planId/submit-and-sign.

15.1 Submit only
----------------

  PATCH /api/overtime/plans/:planId/submit

  Body:
  {
    "remarks": "Submitted for review."
  }

  Result status:
    submitted_to_supervisor

15.2 Sign an already submitted plan
-----------------------------------

  PATCH /api/overtime/plans/:planId/sign

  Body:
  {
    "remarks": "I confirm and sign this Employee OT Plan."
  }

  Signing records the saved signature file path. It does not upload a new image
  and does not change the submitted_to_supervisor status.

Separate calls are not atomic together. If submit succeeds but sign fails, the
plan can remain submitted without an active employee signature. The preferred
submit-and-sign endpoint prevents this state.

=============================

1. POST /api/auth/login
2. Store the JWT and send it as Authorization: Bearer <token>.
3. GET /api/auth/me
4. GET /api/overtime/employees/me

6. GET /api/overtime/plans with the selected date filters.

8. GET /api/overtime/plans/:planId and retain updatedAt.
9. PUT /api/overtime/plans/:planId/draft with expectedUpdatedAt when editing.
10. PATCH /api/overtime/plans/:planId/submit-and-sign after confirmation.
11. Refresh plan detail, plan list, calendar, and notifications after mutations.
12. Allow PATCH /withdraw only while status is submitted_to_supervisor.
13. Display workflowProgress from plan detail instead of reconstructing approval
    stages in the frontend.
14. Use GET /api/notifications or GET /api/notifications/unread-count on normal
    browser refresh or client refetch; realtime is not required.


FRONTEND IMPLEMENTATION NOTES
=============================

Use role === "user" for employee accounts.

Use user.hasEmployeeProfile and user.employeeId from login or /api/auth/me to
confirm account readiness. Load the complete employee profile from
GET /api/overtime/employees/me.

Do not ask a normal user to select departmentId or employeeId. The backend derives
both from the authenticated employee profile and prevents cross-employee writes.

Use the preferred atomic draft routes for the calendar editor. Use the granular
item endpoints only when a client intentionally saves each row separately.

Use submit-and-sign as the normal submission action. The legacy submit and sign
routes are documented only for compatibility and manual API testing.

After a successful withdrawal, treat the returned plan as draft and refetch its
workflowProgress. The previous active signature record is superseded and a new
signature record will be created on the next submit-and-sign operation.

Use updatedAt as a concurrency version when replacing a draft. On
PLAN_VERSION_CONFLICT, reload the latest detail before allowing another save.

The API intentionally exposes planId in URLs such as:
  /employee/plans/PLAN-...

This is normal resource routing. Authorization is enforced on every detail and
mutation endpoint; knowing a plan ID does not grant access.
